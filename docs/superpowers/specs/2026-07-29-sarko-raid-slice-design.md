**SARKO** — от «саркофаг» (укрытие над 4-м энергоблоком ЧАЭС). Смысл двойной:
саркофаг = укрытие = убежище игрока в игре.

**Известный минус:** «Sarko» — прозвище Николя Саркози. Фоновый шум, не блокер.

## 3. Срез 1: цель и критерии успеха

**Цель:** проверить, весело ли играть — за недели и без затрат на серверы, но так, чтобы
мультиплеер потом **включался, а не переписывался**.

**Критерии успеха:**

1. Полный цикл на реальном iPhone: убежище → лоадаут → рейд → лут → бой → эвакуация
   или смерть → схрон корректно обновился.
2. При смерти теряется всё, кроме сейф-кармана — проверено сверкой с данными бэкенда.
3. 60 FPS на iPhone 12 и новее.
4. **Тест фана:** после 10 рейдов подряд есть ответ на «хочется ещё?».

Если критерий 4 не выполнен — срез всё равно успешен: он дёшево показал, что механику
надо менять, до постройки мультиплеера.

## 4. Журнал ключевых решений

| Решение | Причина |
|---|---|
| **Срез = рейд с ботами, но на репликации** | Проверяем фан за недели. Пишем через server-authority, поэтому Dedicated Server позже — смена таргета сборки, не рефактор. |
| **C++ ядро, Blueprints только визуал, данные в CSV** | Blueprints — бинарные `.uasset`: агент не может их писать и ревьюить, git не может мержить. C++ и CSV — текст. Инверсия исходного плана, сделана осознанно. |
| **ИИ-враги со стрельбой сразу** (решение владельца, против рекомендации) | Честный тест жанра. Компенсируется лимитом: 1 враг, 1 оружие, hitscan. |
| **ИИ на C++ state machine, не Behavior Tree** | BT, Blackboard, StateTree — бинарные ассеты. Стейт-машина на C++ — текст. |
| **Управление: левый стик + drag-to-aim, автоогня нет** | Требование владельца: игрок сам бегает, крутится, стреляет. Схема Brawl Stars — проверенный бест-практис. |
| **При смерти теряется всё, кроме сейф-кармана на 1–2 предмета** | Сохраняет риск, не выжигает новичка. Даёт уникальную эмоцию: «какую деталь для гаража спасти». |
| **Схрон на Go-бэкенде с первого дня** (вариант B) | Go — сильная сторона владельца. Правильная модель данных сразу, нулевая миграция потом. |
| **`IStashStorage` с локальной реализацией остаётся** | Иначе нельзя итерировать по геймплею без сети или при лежащем бэкенде. |
| **Инвентарь слот+вес, не тетрис-сетка** | Drag-and-drop сетка на 6″ экране — недели UI и мучение пальцем. Слоты+вес дают ту же жадность за дни. Поля `width`/`height` в данных сразу → сетка позже без миграции. |

### Зафиксированная иллюзия

Серверный схрон в срезе 1 **почти не защищает от читеров**: пока нет Dedicated Server,
хостом матча является устройство игрока — результат отправляет его же клиент, он может
соврать. Защита появится только с реальным Dedicated Server. Что вариант B даёт сейчас:
правильная модель данных, прогресс между устройствами, нулевая миграция позже.

## 6. UE-сторона

### 6.1 Рейд (репликация, server-authority)

| Класс | Единственная ответственность |
|---|---|
| `ASarkoCharacter` | движение, здоровье, смерть |
| `USarkoInventoryComponent` | предметы, вес, сейф-карман; реплицируется **только владельцу** |
| `ASarkoWeapon` | hitscan-выстрел, магазин, перезарядка; выстрел = Server RPC |
| `ASarkoLootContainer` | лут роллится **на сервере в момент вскрытия** |
| `ASarkoExtractionZone` | зона эвакуации + таймер удержания |
| `ASarkoRaidGameMode` | только на сервере: старт/конец рейда, исход |
| `ASarkoRaidGameState` | таймер рейда, реплицируется всем |
| `ASarkoPlayerState` | идентичность игрока |
| `ASarkoAIController` + `ASarkoEnemyCharacter` | C++ state machine: idle → патруль → преследование → стрельба |

**Почему лут роллится при вскрытии:** сгенерированное заранее содержимое уедет клиентам
в репликации и читается из памяти — карта лута станет известна.

### 6.2 Убежище (оффлайн, UI)

| Класс | Ответственность |
|---|---|
| `USarkoStashSubsystem` | схрон в памяти + синхронизация |
| `IStashStorage` | интерфейс: `LoadProfile` / `StartRaid` / `SubmitResult` / `CraftVehicle` |
| `FHttpStashStorage` | прод: HTTP к `sarko-api` |
| `FLocalStashStorage` | дев: локальный `SaveGame`, работает без сети |
| `USarkoGarageSubsystem` | сборка транспорта из деталей, разблокировка карт |

### 6.3 Данные — CSV, не бинарные ассеты

`items.csv` · `loot_tables.csv` · `weapons.csv` · `enemies.csv` · `vehicles.csv`

Правятся агентом, видны в git-диффе, баланс крутится без редактора.
В `items.csv` заложены неиспользуемые поля `width`/`height` — под будущую сетку.

## 7. Контракт `sarko-api`

```
POST /v1/auth/anonymous  → device-scoped JWT
GET  /v1/profile         → схрон, гараж, открытые карты, schema_version
POST /v1/raid/start      → raid_session_token + seed; СПИСЫВАЕТ лоадаут из схрона
POST /v1/raid/result     → (требует token) исход + выжившие предметы → в схрон
POST /v1/garage/craft    → потратить детали, продвинуть транспорт
```

Таблицы: `players`, `stash_items`, `garage_progress`, `raid_sessions`.

### Три защиты от дюпа

1. Лоадаут **списывается при входе**, не при выходе — иначе одну винтовку можно взять
   в два рейда одновременно. Списание обратимо только через механизм `pending`-сессии
   из §11 (если рейд фактически не начался).
2. `raid_session_token` **одноразовый**, гасится после приёма результата.
3. `POST /v1/raid/result` **идемпотентен** по session id — обрыв сети не удвоит лут.

### Готовность к Dedicated Server

`raid_session_token` выдаётся на старте рейда. Сейчас его держит клиент. С появлением
Dedicated Server токен уходит серверу, клиент теряет возможность врать про исход.
**Схема БД и endpoints не меняются** — миграция только в том, кто держит токен.

## 8. Поток рейда

```
УБЕЖИЩЕ (оффлайн)
  LoadProfile() → схрон, гараж, открытые карты
  игрок собирает лоадаут, выбирает карту (доступные — по транспорту)
        ↓
POST /v1/raid/start {map, loadout[]}
  валидация «предметы реально в схроне» → списание → raid_session_token + seed
        ↓
РЕЙД (OpenLevel ?listen — клиент как Listen Server)
  seed → детерминированный спавн контейнеров и врагов
  бег / стрельба / вскрытие контейнеров / укладка сейф-кармана
        ↓
  ├─ ЭВАК:    постоял в зоне 10 сек   → outcome=extracted, весь инвентарь
  ├─ СМЕРТЬ:  HP ≤ 0                  → outcome=died, только сейф-карман
  └─ ТАЙМАУТ: время вышло             → outcome=died
        ↓
POST /v1/raid/result {token, outcome, items[]}   (идемпотентно)
  запись в схрон, гашение токена → возврат в убежище
```

## 9. Управление (iPhone, ландшафт)

Схема Brawl Stars. **Автоогня и автоприцела нет.**

```
┌──────────────────────────────────────────────────────────┐
│ ☢ 0.42 Sv    ⏱ 08:41            🎒 14.2/20 кг   ▮▮▮▯ HP │  ← вся инфа сверху
│                    [ ИГРОВОЕ ПОЛЕ ]                      │
│                       ╱ прицельный конус                 │
│                      ◉ персонаж                          │
│   ╭─────╮                                    ╭─────╮    │
│   │  ⊕  │ движение                    огонь  │  ⊕  │    │
│   ╰─────╯ (плавающий)              (drag-aim) ╰─────╯   │
└──────────────────────────────────────────────────────────┘
```

Время удержания зоны эвакуации (10 сек), длительность рейда и вес-лимиты — тюнящиеся
параметры в конфиге, не константы в коде.

- **Потянул и отпустил** → прицелился вручную и выстрелил; пока тянешь — виден конус.
- **Коротко тапнул** → быстрый выстрел по направлению взгляда (не автоприцел).
- Персонаж смотрит в сторону прицела при прицеливании, иначе — в сторону движения.

Обязательные правила:

| Правило | Причина |
|---|---|
| Плавающие стики (база там, где лёг палец) | Фиксированные стики на телефоне — известный провал |
| Прицельный индикатор на земле | На тач-экране нет курсора |
| Нижние углы — мёртвая зона для HUD | Их закрывают большие пальцы |
| Магнетизм ±5–8°, считается **на сервере** | Компенсирует неточность пальца, одинаков для всех → не преимущество в PvP |
| Скилл в позиционировании, не в пикселях | Иначе выигрывает тот, у кого планшет |
| Учитывать safe area (Dynamic Island, свайп-бар) | Иначе UI не нажимается |

Реализация: Enhanced Input + два `UUserWidget`-стика; стрельба и магнетизм — C++ на сервере.

**Улучшения потом:** разброс от движения (стоя точнее → тактика «остановись, чтобы попасть»),
приседание, разные конусы у оружия.

**План отката:** если через 2 недели бой на тачскрине неуправляем — основной угрозой
становится радиация и среда; система урона к этому готова.

## 10. Границы доверия

| Что | Истина | Причина |
|---|---|---|
| Движение | клиент предсказывает, сервер валидирует | иначе управление вязкое |
| Выстрел и урон | **сервер** | иначе aimbot тривиален |
| Содержимое лута | **сервер, при вскрытии** | иначе карта лута читается из памяти |
| Вес и скорость | **сервер** | иначе бесконечный рюкзак |
| Схрон и гараж | **sarko-api** | иначе прогресс подделывается |
| Эффекты, звук, тряска | клиент, мгновенно | отзывчивость важнее точности |

**Отдельно:** выстрел рисуется у клиента сразу, не дожидаясь сервера — иначе бой тормозной.

## 11. Обработка ошибок

Для extraction-игры это половина дизайна: здесь живёт доверие игрока к сохранности лута.

| Кейс | Решение |
|---|---|
| **Обрыв сети в рейде** (метро, лифт) | Рейд идёт локально, не ломается. Результат → в локальную очередь, ретраится. Идемпотентность не даст удвоить лут. |
| **Выход из приложения посреди рейда** | **Выход = смерть.** Иначе идеальный чит: набрал лут → убили → убил приложение. Реализация: `raid_sessions.expires_at`; нет результата за (длительность + буфер) → сервер закрывает как `died`. |
| **`raid/start` прошёл, игра упала до входа** | Сессия создаётся как `pending`, подтверждается при фактическом входе. Нет подтверждения 60 с → **лоадаут возвращается автоматически**. |
| **Бэкенд недоступен** | В рейд не пускаем, показываем «нет связи». Иначе игрок отыграет рейд, а результат потеряется. |
| **Миграции данных** | В профиле `schema_version` — модель можно менять, не ломая сохранения тестеров. |

## 12. Монетизация — предупреждения на будущее (подпроект 5)

Не реализуется в срезе 1, фиксируется, чтобы не построить P2W случайно.

1. **«Большой схрон» по подписке — не чистый non-P2W.** Размер схрона и доступ к картам =
   экономическое преимущество: больше вынес → лучше снаряга → сильнее в PvP. Формально
   Apple пропустит, игроки назовут P2W. Решать дизайном.
2. **Размер сейф-кармана продавать нельзя ни в каком виде.** Платный безопасный контейнер
   напрямую снижает риск потери — именно за это Tarkov годами получает обвинения в P2W.
   Сейф-карман **зарабатывается игрой**, одинаково для всех.
3. **Магнетизм прицела одинаков для всех и считается на сервере** — никогда не предмет продажи.

## 13. Мультиплеер и хостинг — findings (подпроект 3)

Исследовано 2026-07-29, чтобы архитектура среза 1 не противоречила будущему.

### Railway не подходит для игровых серверов

Railway отдаёт наружу HTTP и TCP-прокси, **но не UDP**, а игровой трафик Unreal — UDP.
Плюс там цикл build→deploy, а не оркестрация инстансов под матч.
*(Требует подтверждения в доках Railway — MCP был недоступен при написании.)*

**Вывод:** `sarko-api` на Railway ✅, игровые серверы — в другом месте.

### Исправление исходной спеки

> «отдельный сервер; после окончания сервер уничтожается»

Верно про **процесс**, а не про **машину**. Виртуалка на матч — разорительно и медленно
(старт VM 30–60 с). Правильно: **одна машина держит десятки процессов-матчей**, каждый
на своём порту, процесс умирает после рейда.

### Модель матчмейкинга (как в Таркове)

Игрок **не видит списка серверов**, он выбирает карту:

```
выбор карты → очередь → матчмейкер собирает 10–15 игроков (карта + регион + пинг)
→ аллокатор поднимает процесс, отдаёт IP:порт → матч → сервер умирает
```

### Оценка стоимости (модель)

- рейд ≈ 12 минут с загрузкой
- 500 рейдов/день → 100 инстанс-часов/день → в среднем ~4 одновременных матча,
  в пике ×3–4 → ~15
- top-down, 15 игроков, тик 20–30 Гц, headless → ~250–400 MB RAM и ~0.2–0.4 ядра на матч
- 15 матчей ≈ 6 GB RAM, ~5 ядер

**Вывод: один выделенный сервер за €40–50/мес держит ~500 рейдов в день** — при условии
плотности процессов, а не VM на матч.

### Варианты хостинга

| Вариант | Цена | Когда |
|---|---|---|
| **Edgegap / Hathora** (оплата за минуты) | ~0 при нуле игроков | **старт** |
| **Hetzner / OVH** + свой аллокатор на Go | €40–50/мес фикс | **при стабильной нагрузке** |
| AWS GameLift / Agones на k8s | дорого / сложно | не для соло-разработчика |
| P2P, игрок-хост | бесплатно | **нельзя**: хост читерит, лут на ставке |

### Бест-практис экономии

1. **Плотность процессов** на машине — главный рычаг, экономит в 10+ раз.
2. **Тёплый пул** 1–2 серверов: холодный старт UE-сервера 5–20 с, игроки не терпят.
3. **Один регион на старте** (EU): каждый регион умножает простой.
4. **Не AWS/GCP для игрового трафика** — исходящий трафик съест бюджет; у Hetzner/OVH
   включены десятки ТБ.
5. **Тик 20–30 Гц, не 60** — для top-down разницы не видно, нагрузка вдвое ниже.

## 14. Тестирование

Ключевое ограничение: **агент не может кликать в редакторе UE.** Тестируемость заложена
в архитектуру, а не добавлена сверху.

### 14.1 Что проверяет агент сам

**Чистая логика вынесена из UE-акторов** в обычные C++ классы без зависимости от `UObject`
там, где возможно: ролл лута, расчёт веса, добавление/удаление предметов, правила
сейф-кармана, требования сборки транспорта.

Поверх — UE Automation Tests, запускаются headless:

```
UnrealEditor-Cmd Sarko.uproject \
  -ExecCmds="Automation RunTests Sarko" \
  -unattended -nullrhi -testexit="Automation Test Queue Empty"
```

`-nullrhi` = без рендера, значит агент проверяет свою работу без GUI.

**Go-бэкенд:** табличные тесты Go, покрытие полное — тут живут прогресс и защита от дюпа
(списание при входе, идемпотентность, истечение сессии, авто-возврат лоадаута).

**Контракт UE ↔ Go:** Go-сторона через `httptest`; UE-сторона имеет фейковую реализацию
`IStashStorage` для автотестов.

### 14.2 Что может проверить только человек

| Что | Как |
|---|---|
| Весело или нет | 10 рейдов подряд, ответ на «хочется ещё?» |
| Управление большими пальцами | реальное устройство, не редактор |
| Читается ли прицельный конус | визуально на солнце и в темноте |
| Производительность | `stat unit` на iPhone: FPS, кадровое время, память, нагрев |

Под каждую веху агент выдаёт письменный чеклист ручной проверки.

### 14.3 Бюджет производительности

Цель: **60 FPS на iPhone 12 и новее.** Mobile-рендерер; Nanite и Lumen выключены.
Замеры делает человек на устройстве.

## 16. Окружение и блокеры

Проверено на машине 2026-07-29.

| Что | Статус | Действие |
|---|---|---|
| **Место на диске** | 🛑 **занято 378 из 460 GiB, свободно 30 GiB (93%)** | освободить **~100 GiB** или внешний SSD |
| **Unreal Engine** | 🛑 не установлен (нет Epic Launcher) | установить UE 5.8 с iOS-платформой |
| **git-lfs** | ⚠️ не установлен | `brew install git-lfs` (brew есть) |
| Xcode | ✅ 26.6 | ок |
| Железо | ✅ arm64, 32 GB RAM | ок |
| Apple Developer | ⚠️ нужен позже ($99/год) | для прототипа хватит бесплатного профиля (сборки живут 7 дней) |

**Почему 30 GiB не хватит:** движок с iOS-платформой 35–45 GB, плюс Derived Data Cache
проекта, растущий до 10–40 GB, плюс промежуточные файлы Xcode. Комфортный минимум —
**80–100 GiB свободно**. Ниже ~10 GiB macOS деградирует.

**Диск — единственное, что стоит между спекой и первой строкой кода.**

### Mac как платформа разработки

Для игры под iOS **Mac обязателен**: собрать и подписать `.ipa` можно только на macOS.
Работает нативно: редактор UE, компиляция C++, сборка и запуск на iPhone, локальный тест
мультиплеера в нескольких окнах.

**Единственное ограничение:** Linux-сборку Dedicated Server с macOS собрать нельзя —
кросс-компиляционного тулчейна нет. Решается CI: GitHub Actions на Linux-раннере.
В срезе 1 сервера нет, поэтому не блокер.

## 17. Риски

| Риск | Вероятность | Смягчение |
|---|---|---|
| Бой на тачскрине неуправляем | средняя | план отката на радиацию как основную угрозу (§9) |
| Стрельба + ИИ съедят весь срез | **высокая** | лимит: 1 враг, 1 оружие, hitscan, без баллистики |
| UE C++ тормозит из-за нулевого опыта | средняя | логика на агенте, человек ревьюит и работает в редакторе |
| Диск закончится посреди работы | **высокая, если не расчистить** | освободить 100 GiB до старта |
| Объём расползётся на мультиплеер | средняя | §15 — жёсткая граница |
| Проект окажется не весёлым | средняя | это и есть цель среза: узнать дёшево и рано |
